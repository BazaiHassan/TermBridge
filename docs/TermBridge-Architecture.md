# TermBridge — سند معماری و پرامپت ساخت پروژه

> این فایل به عنوان **پرامپت مرجع** برای ساخت پروژه استفاده می‌شود. هر بخش قابل استناد است و
> پیاده‌سازی باید دقیقاً از قراردادهای این سند (نام‌ها، شماره‌ی opcodeها، ساختار پوشه‌ها) پیروی کند.

---

## ۱. خلاصه‌ی محصول

**TermBridge** یک سیستم دسترسی از راه دور به ترمینال است. کاربر روی لپ‌تاپ (ویندوز یا لینوکس) یک
ایجنت کوچک اجرا می‌کند، با گوشی اندروید یک QR را اسکن می‌کند، و از آن پس شل کامل آن ماشین را
روی موبایل در اختیار دارد.

**تفاوت با AnyDesk:** هیچ فریم تصویری منتقل نمی‌شود؛ فقط جریان بایت‌های ترمینال. مصرف پهنای باند
در حد چند کیلوبایت بر ثانیه و تأخیر عملاً برابر RTT شبکه است.

**تفاوت با SSH/Termius:** نیازی به IP ثابت، port forwarding، باز کردن پورت روی فایروال، یا
مدیریت دستی کلید نیست. جفت‌سازی با یک بار اسکن QR انجام می‌شود و اتصال از پشت NAT هم کار می‌کند.

### اهداف اصلی (ترتیب اولویت)
1. **بدون کانفیگ بودن** — از نصب تا اولین اتصال زیر ۶۰ ثانیه.
2. **تأخیر پایین** — زمان بین فشردن کلید تا دیدن echo زیر ۵۰ms روی LAN.
3. **امنیت** — رمزنگاری سرتاسری؛ سرور واسط نباید توان خواندن محتوا داشته باشد.
4. **قابل استفاده بودن روی موبایل** — کیبورد و تعامل لمسی باید واقعاً کار کند، نه اینکه فقط «کار کند».

### خارج از محدوده (Non-goals) — فاز یک
- انتقال فایل، پورت فورواردینگ، اشتراک صفحه‌ی گرافیکی
- نسخه‌ی iOS و دسکتاپ کلاینت
- چند کاربره بودن یا مدیریت تیمی

```

│   Android App (Kotlin)   │          │    Agent (Go)            │
│   ─ Terminal emulator    │          │    ─ PTY / ConPTY        │
│   ─ QR scanner           │          │    ─ Session manager     │
│   ─ Key row / gestures   │          │    ─ WS server (LAN)     │
└────────────┬─────────────┘          └────────────┬─────────────┘
             │                                     │
             │  ── مسیر ۱: LAN مستقیم (mDNS) ──    │
             ├─────────────────────────────────────┤
             │                                     │
             │  ── مسیر ۲: از طریق Relay ──        │
             │        ┌──────────────────┐         │
             └───────►│  Relay (Go/VPS)  │◄────────┘
                      │  ─ فقط bridge    │
                      │  ─ کور به محتوا  │
                      └──────────────────┘
```

سه ماژول مستقل:

| ماژول | زبان | نقش |
|---|---|---|
| `agent` | Go 1.22+ | اجرا روی لپ‌تاپ، مدیریت PTY، سرور WebSocket محلی |
| `relay` | Go 1.22+ | سرور واسط روی VPS برای عبور از NAT |
| `app` | Kotlin | اپ اندروید |

**هر سه در یک monorepo.** پروتکل مشترک به صورت یک سند واحد (`docs/PROTOCOL.md`) نگهداری می‌شود
و پیاده‌سازی Go و Kotlin هر دو باید با آن سازگار بمانند.

## ۳. جریان‌های اصلی کاربر

### ۳.۱ جفت‌سازی (Pairing)
1. کاربر روی لپ‌تاپ اجرا می‌کند: `termbridge pair`
2. ایجنت یک `pairing_code` تصادفی ۶ بایتی می‌سازد، معتبر به مدت ۱۲۰ ثانیه.
3. ایجنت یک QR را به صورت ASCII در ترمینال چاپ می‌کند حاوی:
   ```json
   {
     "v": 1,
     "agent_id": "<base64 of Ed25519 public key>",
     "name": "amir-thinkpad",
     "code": "<base64 pairing_code>",
     "lan": ["192.168.1.20:7423"],
     "relay": "wss://relay.termbridge.io"
   }
   ```
4. اپ QR را اسکن می‌کند، دست‌دادن Noise را انجام می‌دهد، کلید عمومی خودش را ثبت می‌کند.
5. ایجنت کلید عمومی گوشی را در `trusted_devices` ذخیره می‌کند. `pairing_code` بلافاصله باطل می‌شود.

> پس از جفت‌سازی، اتصال‌های بعدی بدون QR و فقط با کلیدها انجام می‌شوند.

### ۳.۲ اتصال
اپ به صورت **موازی** هر دو مسیر را امتحان می‌کند و اولی که handshake را تمام کند برنده است
(الگوی Happy Eyeballs):
- **مسیر LAN:** جست‌وجوی mDNS برای `_termbridge._tcp.local`، سپس اتصال مستقیم به IP لوکال.
- **مسیر Relay:** اتصال به relay و درخواست اتصال به `agent_id`.

اگر LAN برنده شد، اتصال relay بسته می‌شود. تعویض مسیر وسط کار (مثلاً خروج از خانه) در فاز ۳.

### ۳.۳ کار با ترمینال
- اتصال باز می‌شود → یک session پیش‌فرض ساخته می‌شود → شل کاربر اجرا می‌شود.
- کلیدها به صورت بایت خام به PTY فرستاده می‌شوند.
- خروجی PTY به صورت جریان به اپ می‌رسد و توسط شبیه‌ساز VT رندر می‌شود.
- چرخش صفحه یا باز شدن کیبورد → فریم `RESIZE` فرستاده می‌شود.

## ۴. پروتکل TermBridge (نسخه ۱)

### ۴.۱ لایه‌ها
```
[ WebSocket binary frames ]
        ↑
[ Noise Protocol IK — رمزنگاری سرتاسری ]
        ↑
[ TermBridge framing — opcodeها ]
```
حتی وقتی از relay رد می‌شویم، لایه‌ی Noise سرتاسری است؛ relay فقط بایت‌های رمزشده را جابه‌جا می‌کند.
روی LAN هم همان Noise استفاده می‌شود تا یک مسیر کد مشترک داشته باشیم.

### ۴.۲ ساختار فریم

```
+--------+-----------+------------------+
| opcode | sessionID |    payload       |
| 1 byte |  1 byte   |   0..N bytes     |
+--------+-----------+------------------+
```
- `sessionID = 0` یعنی فریم کنترلی سطح اتصال (نه مربوط به یک session خاص).
- حداکثر اندازه‌ی payload: ۶۴ کیلوبایت.
- همه‌ی اعداد چندبایتی **big-endian** هستند.

### ۴.۳ جدول opcodeها

| کد | نام | جهت | payload |
|---|---|---|---|
| `0x01` | `DATA` | دوطرفه | بایت‌های خام ترمینال |
| `0x02` | `RESIZE` | app → agent | `uint16 cols, uint16 rows` |
| `0x10` | `SESSION_OPEN` | app → agent | JSON: `{"shell": "", "cwd": "", "cols": 80, "rows": 24}` |
| `0x11` | `SESSION_OPENED` | agent → app | `uint8 sessionID` |
| `0x12` | `SESSION_CLOSE` | دوطرفه | — |
| `0x13` | `SESSION_EXIT` | agent → app | `int32 exitCode` |
| `0x20` | `PING` | دوطرفه | `uint64` timestamp میلی‌ثانیه |
| `0x21` | `PONG` | دوطرفه | همان timestamp دریافتی |
| `0x30` | `HELLO` | app → agent | JSON: `{"v":1, "client":"android/1.0.0"}` |
| `0x31` | `HELLO_ACK` | agent → app | JSON: `{"v":1, "agent":"...", "os":"linux", "hostname":"..."}` |
| `0x40` | `ERROR` | agent → app | JSON: `{"code":"...", "msg":"..."}` |

### ۴.۴ قواعد جریان
- **Keepalive:** اپ هر ۱۵ ثانیه `PING` می‌فرستد. اگر ۳ پاسخ پشت سر هم نیاید، اتصال مرده تلقی می‌شود.
- **Coalescing خروجی:** ایجنت خروجی PTY را با یک تایمر ۵ میلی‌ثانیه‌ای تجمیع می‌کند تا در خروجی
  پرحجم (مثل `cat` روی فایل بزرگ) هزاران فریم کوچک نفرستد. اما اگر بافر خالی بود، اولین بایت
  **بدون تأخیر** ارسال می‌شود تا echo کلید کند نشود.
- **ورودی هرگز تجمیع نمی‌شود.** هر کلید بلافاصله فرستاده می‌شود.
- **Backpressure:** اگر صف ارسال از ۴ مگابایت گذشت، ایجنت خواندن از PTY را موقتاً متوقف می‌کند.

## ۵. ماژول Agent (Go)

### ۵.۱ ساختار پوشه
```
agent/
├── cmd/termbridge/main.go        # CLI: pair | run | status | reset
├── internal/
│   ├── pty/
│   │   ├── pty.go                # interface مشترک
│   │   ├── pty_unix.go           # build tag: linux darwin
│   │   └── pty_windows.go        # ConPTY
│   ├── session/manager.go        # ساخت/بستن/نگاشت sessionID
│   ├── proto/                    # encode/decode فریم‌ها (مشترک با relay)
│   ├── transport/
│   │   ├── wsserver.go           # سرور LAN
│   │   ├── relayclient.go        # اتصال خروجی به relay
│   │   └── noise.go              # handshake و رمزنگاری
│   ├── discovery/mdns.go         # تبلیغ سرویس در LAN
│   ├── pairing/pairing.go        # کد جفت‌سازی + تولید QR
│   └── store/store.go            # کلیدها و دستگاه‌های مورد اعتماد
└── go.mod
```

### ۵.۲ کتابخانه‌های پیشنهادی
| نیاز | پکیج |
|---|---|
| PTY یونیکس | `github.com/creack/pty` |
| ConPTY ویندوز | `github.com/UserExistsError/conpty` |
| WebSocket | `github.com/coder/websocket` |
| Noise | `github.com/flynn/noise` |
| mDNS | `github.com/grandcat/zeroconf` |
| QR در ترمینال | `github.com/skip2/go-qrcode` + رندر با نویسه‌های نیم‌بلوک |
| CLI | `github.com/spf13/cobra` |

### ۵.۳ انتزاع PTY
یک interface واحد که هر دو پیاده‌سازی از آن پیروی کنند:

```go
type Terminal interface {
    Read(p []byte) (int, error)
    Write(p []byte) (int, error)
    Resize(cols, rows uint16) error
    Wait() (exitCode int, err error)
    Close() error
}

func Start(shell string, args []string, env []string, cwd string, cols, rows uint16) (Terminal, error)
```

**نکات پیاده‌سازی ویندوز:**
- ConPTY نیاز به ویندوز ۱۰ نسخه 1809 (build 17763) به بالا دارد. اگر نسخه پایین‌تر بود، با
  پیام خطای واضح خارج شو؛ سراغ راه‌حل‌های جایگزین مثل winpty نرو.
- شل پیش‌فرض: `powershell.exe`، قابل تغییر با فلگ `--shell`.
- متغیر `TERM=xterm-256color` را ست کن.

**نکات یونیکس:**
- شل پیش‌فرض از `$SHELL` و در نبود آن `/bin/bash`.
- شل را به صورت login shell اجرا کن (`-l`) تا پروفایل کاربر بارگذاری شود.
- سیگنال `SIGWINCH` بعد از هر resize.

### ۵.۴ فایل پیکربندی و کلیدها
مسیر:
- لینوکس: `~/.config/termbridge/`
- ویندوز: `%APPDATA%\TermBridge\`

```
config.json        # تنظیمات کاربر
identity.key       # کلید خصوصی Ed25519 (مجوز 0600)
devices.json       # لیست دستگاه‌های جفت‌شده
```

```json
// devices.json
[
  {
    "pubkey": "base64...",
    "name": "Pixel 8",
    "paired_at": "2026-09-14T10:00:00Z",
    "last_seen": "2026-09-14T12:30:00Z"
  }
]
```

### ۵.۵ دستورات CLI
```
termbridge pair            # نمایش QR و انتظار برای جفت‌سازی
termbridge run             # اجرای ایجنت (حالت عادی، پس از جفت‌سازی)
termbridge run --lan-only  # بدون relay
termbridge status          # وضعیت اتصال و لیست دستگاه‌ها
termbridge revoke <name>   # حذف یک دستگاه
termbridge reset           # پاک کردن کامل کلیدها و دستگاه‌ها
```

## ۶. ماژول Relay (Go)

سرور بسیار ساده و **بدون حالت معنادار**. تنها وظیفه: به هم رساندن دو سوکت.

```
relay/
├── cmd/relay/main.go
└── internal/
    ├── hub/hub.go       # map[agentID]*conn + جفت کردن
    └── ws/handler.go
```

### رفتار
1. ایجنت به `wss://relay/agent` وصل می‌شود، خود را با امضای Ed25519 روی یک nonce معرفی می‌کند،
   و منتظر می‌ماند.
2. اپ به `wss://relay/client?agent=<agentID>` وصل می‌شود.
3. relay دو سوکت را جفت می‌کند و از آن به بعد فقط بایت‌ها را کپی می‌کند.

### قواعد
- relay **کلید Noise ندارد** و نمی‌تواند محتوا را بخواند. این باید در تست‌ها تأیید شود.
- محدودیت نرخ: حداکثر ۵ اتصال همزمان و ۱۰ مگابیت بر ثانیه به ازای هر agentID.
- هیچ لاگی از محتوا نوشته نمی‌شود؛ فقط متادیتای اتصال با سطح `info`.
- استقرار: یک باینری + یک فایل systemd + Caddy برای TLS.

## ۷. ماژول اپ اندروید (Kotlin)

### ۷.۱ مشخصات پایه
- `minSdk = 26`، `targetSdk = 35`
- Kotlin + **Jetpack Compose** برای UI
- معماری: MVVM + `StateFlow`، تک‌اکتیویتی
- DI: Hilt

### ۷.۲ ساختار ماژول‌ها
```
app/
├── core-proto/        # کدک فریم‌ها (آینه‌ی internal/proto در Go)
├── core-crypto/       # Noise + مدیریت کلید در Keystore
├── core-transport/    # کلاینت WebSocket، کشف mDNS، منطق Happy Eyeballs
├── core-terminal/     # شبیه‌ساز VT + بافر صفحه + scrollback
├── feature-pairing/   # اسکن QR
├── feature-terminal/  # صفحه‌ی اصلی ترمینال
├── feature-devices/   # لیست و مدیریت دستگاه‌ها
└── app/               # اسمبلی نهایی، ناوبری
```

### ۷.۳ شبیه‌ساز ترمینال — تصمیم مهم

سه گزینه، به ترتیب توصیه:

1. **نوشتن پارسر اختصاصی VT (توصیه‌شده).** یک state machine برای escape sequenceها + یک
   بافر صفحه‌ی `Array<CharArray>` + رندر با `Canvas.drawText` روی یک `View` سفارشی.
   پوشش لازم برای فاز یک: CSI (حرکت مکان‌نما، پاک کردن، SGR رنگ ۱۶/۲۵۶/truecolor)،
   حالت‌های DEC (alternate screen، bracketed paste)، عنوان OSC. کنترل کامل و بدون مسئله‌ی لایسنس.
2. **استفاده از `terminal-emulator` پروژه‌ی Termux.** بالغ و تست‌شده، اما **GPLv3** است و کل اپ
   را آلوده می‌کند. فقط اگر پروژه open-source با همان لایسنس است.
3. **xterm.js داخل WebView.** سریع‌ترین راه برای MVP اما کندتر، پرمصرف‌تر، و ادغام کیبورد
   دردسرساز است. **برای نسخه‌ی نهایی انتخاب نکن.**

مسیر پیشنهادی: فاز ۱ با پارسر اختصاصی شروع کن ولی دامنه را کوچک نگه دار (فقط چیزی که
`bash`, `vim`, `htop`, `top`, `less` لازم دارند).

**الزامات رندر:**
- فونت monospace با `Typeface` — JetBrains Mono یا Fira Code به صورت asset.
- رندر فقط ناحیه‌ی dirty، نه کل صفحه.
- scrollback حداقل ۱۰۰۰۰ خط با بافر حلقوی.
- انتخاب متن با لمس طولانی + کپی به کلیپ‌بورد.

### ۷.۴ کیبورد — بحرانی‌ترین بخش UX

این بخشی است که اکثر اپ‌های مشابه در آن شکست می‌خورند. الزامات:

- **ردیف کلید اضافی** بالای کیبورد سیستمی، همیشه قابل مشاهده:
  ```
  [Esc] [Tab] [Ctrl] [Alt] [←] [↓] [↑] [→] [/] [|] [-] [~] [Ctrl+C] [⋯]
  ```
- `Ctrl` و `Alt` باید **sticky** باشند: یک بار زدن = فعال برای کلید بعدی، دو بار زدن = قفل.
- دکمه‌ی `⋯` یک شیت با کلیدهای کمتراستفاده باز کند: F1–F12، Home/End، PgUp/PgDn، Insert، Delete.
- `EditText` نامرئی با `inputType = TYPE_NULL` و `IME_FLAG_NO_EXTRACT_UI` برای گرفتن ورودی خام؛
  autocorrect و predictive text باید کاملاً خاموش باشند.
- ژست‌ها: کشیدن دو انگشتی = اسکرول، pinch = تغییر اندازه‌ی فونت، سوایپ از لبه = سوئیچ session.

### ۷.۵ سرویس پیش‌زمینه
اتصال داخل یک `ForegroundService` با نوتیفیکیشن دائمی نگهداری می‌شود تا اندروید هنگام رفتن اپ
به پس‌زمینه سوکت را نکشد. نوتیفیکیشن باید نام ماشین متصل و دکمه‌ی «قطع اتصال» را نشان دهد.

### ۷.۶ نگهداری کلیدها
کلید خصوصی دستگاه در **Android Keystore** تولید و نگهداری می‌شود (`StrongBox` اگر موجود بود).
اطلاعات دستگاه‌های جفت‌شده در `EncryptedSharedPreferences`. قفل بیومتریک اختیاری قبل از اتصال.

### ۷.۷ کتابخانه‌ها
| نیاز | کتابخانه |
|---|---|
| WebSocket | OkHttp |
| اسکن QR | CameraX + ML Kit Barcode Scanning |
| mDNS | `NsdManager` (اندروید) |
| Noise | پیاده‌سازی سبک روی Tink/BouncyCastle، یا پورت `noise-java` |
| رمزنگاری ذخیره‌سازی | `androidx.security:security-crypto` |

## ۸. امنیت

این پروژه عملاً یک شل کامل روی ماشین کاربر باز می‌کند. امنیت اختیاری نیست.

### الزامات
1. **رمزنگاری سرتاسری با Noise_IK_25519_ChaChaPoly_BLAKE2s.** کلید ایستای ایجنت در QR منتقل
   می‌شود، پس اپ از همان اولین پیام می‌تواند ایجنت را احراز کند (بدون پنجره‌ی MITM).
2. **کد جفت‌سازی یک‌بارمصرف** با عمر ۱۲۰ ثانیه. پس از مصرف یا انقضا، باطل.
3. **allowlist صریح.** ایجنت فقط اتصال از کلیدهای عمومی موجود در `devices.json` را می‌پذیرد.
   هر چیز دیگری بی‌صدا drop می‌شود.
4. **relay کور است.** هیچ کلید رمزگشایی ندارد. باید یک تست وجود داشته باشد که ثابت کند
   بایت‌های عبوری از relay رمزشده‌اند.
5. **پیوند به LAN.** سرور LAN فقط روی رابط‌های شبکه‌ی محلی bind شود، نه `0.0.0.0` بدون فیلتر.
6. **ابطال (revoke)** باید فوری باشد و اتصال فعال آن دستگاه را ببندد.
7. **بدون بالا بردن سطح دسترسی.** ایجنت با دسترسی همان کاربر اجرا می‌شود، نه root/Administrator.
   در README صریحاً هشدار داده شود که اجرای آن با sudo خطرناک است.
8. **نشانگر دیداری.** تا وقتی session فعال است، ایجنت در ترمینال خود یک خط وضعیت نشان دهد؛
   کاربر نباید بتواند فراموش کند که ماشینش در دسترس است.

### تهدیدهایی که پوشش نمی‌دهیم (در README ذکر شود)
- ماشین یا گوشیِ از پیش آلوده
- حمله‌ی فیزیکی به دستگاه قفل‌نشده
- تحلیل ترافیک روی relay (اندازه و زمان‌بندی بسته‌ها)

## ۹. عملکرد — اهداف قابل اندازه‌گیری

| معیار | هدف |
|---|---|
| تأخیر echo کلید روی LAN | < ۵۰ms |
| تأخیر echo از طریق relay | < RTT + 20ms |
| مصرف داده در تایپ عادی | < ۱ کیلوبایت بر ثانیه |
| زمان اتصال مجدد پس از قطعی | < ۳ ثانیه |
| مصرف RAM ایجنت در حالت بی‌کار | < ۲۰ مگابایت |
| اندازه‌ی باینری ایجنت | < ۱۵ مگابایت |
| اندازه‌ی APK | < ۱۵ مگابایت |

**تله‌های عملکردی که باید از آن‌ها پرهیز کرد:**
- تخصیص حافظه‌ی جدید به ازای هر فریم در Go — از `sync.Pool` استفاده کن.
- رندر کل صفحه در اندروید به ازای هر بایت ورودی — رندر را با `Choreographer` به ۶۰ فریم بر ثانیه مقید کن.
- JSON در مسیر داغ داده — فقط برای پیام‌های کنترلی کم‌تکرار مجاز است.

- `ktlint` + `detekt` در CI
